**The system runs as three applications on one backend image, backed by PostgreSQL, Redis, ClamAV, and Backblaze B2.** The API answers HTTP requests. The worker runs slow background jobs and has no HTTP port. Both processes come from the same Docker image and differ only by the `ROLE` environment variable.

## Why the worker is a separate process

- **Ingestion is CPU-heavy.** Parsing a workbook and resolving indicators blocks the Node event loop for long stretches.
- **Blocking the API would freeze requests.** Running that work inside the API process would delay every HTTP response.
- **Same image, different role.** `src/main.ts` refuses to start with `ROLE=worker`. `src/worker.ts` refuses to start with `ROLE=api`. A wrong setting fails at boot.

## Data stores

| Store | Used for | Durable? |
| --- | --- | --- |
| PostgreSQL 15 + PostGIS | All business data, audit logs, ingestion state, spatial data | Yes. This is the system of record. |
| Redis 7 | BullMQ job queues and short-lived cache | No. Lost jobs are recovered from PostgreSQL state. |
| Backblaze B2 (S3 API) | Uploaded dataset files, avatars, exports | Yes |
| ClamAV | Virus scan of every upload before it is kept | Stateless service |

## External services

| Service | Purpose | Called from |
| --- | --- | --- |
| Termii | SMS one-time codes and SMS notifications | Worker (SMS queue) |
| Resend, Brevo, or SMTP | Transactional email | Worker (notification queue) |
| Anthropic API | AI Health Data Assistant | API |
| Sentry | Error monitoring, when enabled | API and worker |

## Request path, in order

1. The browser calls `https://<host>/api/v1/...`.
2. nginx applies TLS, security headers, and rate limits.
3. The API runs its global guards, validates input, and calls a service.
4. The service reads or writes PostgreSQL, and may enqueue a job in Redis.
5. The worker picks up the job later and writes its result to PostgreSQL.

**Key point: a request never waits for slow work.** It enqueues the job and returns. Progress is read back from PostgreSQL.
