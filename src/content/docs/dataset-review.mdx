**A dataset moves from draft to published through two staff review tiers.** The Validator checks the work and moves it to `validated`. The Approver gives final approval or sends it back. Publishing is a third, separate capability. Every step writes one row to `workflow_actions`.

## Two review tiers

| Tier | Capability | Can do | Cannot do |
| --- | --- | --- | --- |
| Validator | `validate:datasets` | Claim work, run the 8-part QA checklist, mark validated, reject, request revision | Give final approval |
| Approver | `approve:datasets` | Approve with a comment, send back to under review with a comment | Work on pending or under-review items |
| Publisher | `publish:datasets` | Publish an approved dataset to the public catalogue | Approve or validate |

**Key point: `approved` does not mean public.** Only publication sets `published_at` and makes a dataset visible in the public catalogue.

## The QA checklist

The Validator must pass all eight checks before the dataset can move to `validated`:

1. Completeness
2. Accuracy
3. Consistency
4. Timeliness
5. Validity
6. Uniqueness
7. Geo-references
8. Documentation

## Who gets notified

| Event | Who is told |
| --- | --- |
| Dataset becomes `validated` | Staff holding `approve:datasets` |
| Approver sends it back | Staff holding `validate:datasets` |
| Final approval | The submitting development partner's users |
| Rejection or revision request | The submitting development partner's users |

## Ingestion gate

Ingestion runs only for datasets in these statuses: `pending`, `under_review`, or `approved`. A dataset that is `validated` is not in that list, so the ingestion worker refuses to re-ingest it. See [Ingestion overview](/docs/ingestion-overview).

## The review thread

- Every transition writes one `workflow_actions` row: actor, action type, optional comment, and timestamp.
- The dataset page shows this as a timeline. Staff can read the full history of who did what and why.
